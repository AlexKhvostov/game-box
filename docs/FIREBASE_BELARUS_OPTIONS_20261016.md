## Вывод

Подтверждённого способа прямо сейчас подключить полный Firebase Blaze для физлица с реальным белорусским платёжным адресом не найдено. Полная невозможность всех вариантов Firebase также не установлена. Отдельные бесплатные Firebase-сервисы доступны в существующем проекте, CLI успешно авторизован. Проблема — Cloud Billing для платной инфраструктуры.

Рабочая рекомендация агента: сначала проверить реальную активацию Yandex Cloud для белорусского плательщика, затем при подтверждении использовать Firebase Authentication/Remote Config на Spark вместе с доверенным сервером Yandex Cloud Functions и новой YDB Serverless. Это сохраняет Google-вход и настройки Firebase, заменяя платные Functions/Firestore. Альтернатива с фиксированной стоимостью — отдельный VPS у уже используемого Hostland, Node.js и PostgreSQL.

4. Партнёрский биллинг — реальный механизм, предусмотренный Google, однако это не доказательство доступности для конкретного белорусского физлица. Источник: [варианты оплаты и реселлеры](https://docs.cloud.google.com/billing/docs/resources/currency).

### Почему Yandex Cloud рассматривается предметно

[Официальные вопросы по оплате](https://yandex.cloud/ru/docs/billing/qa/payment) прямо указывают расчёты в RUB и карты Белкарт Республики Беларусь/Мир РФ для белорусских налоговых резидентов. Нельзя обещать приём любой карты: банк, тип профиля, верификация и фактический статус аккаунта проверяются при подключении. В разных вкладках/локализациях создания аккаунта сведения о валюте отличаются; окончательный договор и валюту нужно сверить до подтверждения. Не выбирать фиктивное резидентство.

[YDB](https://yandex.cloud/ru/services/ydb) поддерживает транзакции нескольких записей: это позволяет реализовать атомарные начисления, защиту от повторов, владельца покупки и приглашения. [Официальный пример Node.js Functions → YDB](https://yandex.cloud/ru/docs/tutorials/serverless/connect-from-cf-nodejs) подтверждает технический путь; его старую runtime-версию не следует копировать автоматически.

Размещение Firebase Admin SDK на внешнем сервере предусмотрено [документацией Firebase](https://firebase.google.com/docs/admin/setup). Ключи сервисных аккаунтов остаются только в защищённой серверной среде; никаких ключей в APK, Git или публичном конфиге.

Иллюстрация:1млн вызовов по0,5с при256МБ =34,722ГБ×час; после вычета10 — **160,20RUB только Functions**. Это вычисленный сценарий, не замер игры. БД, шлюз, секреты, логи и трафик считаются отдельно; подготовленные постоянно работающие экземпляры не включены.

[Оплата нерезидентами](https://www.hostland.ru/paytypes) разрешена иностранными банковскими картами, но конкретный платёж не проводился.
- [Supabase Pro](https://supabase.com/pricing) — от25USD/месяц; [billing FAQ](https://supabase.com/docs/guides/platform/billing-faq) описывает оплату картой. Факт поддержки платёжного профиля Алексея из этого не следует.

### Сохранение функций Untouch

Firebase Authentication и Remote Config можно оставить на Spark без привязки карты в рамках текущих квот: [тарифы Firebase](https://firebase.google.com/pricing). В текущем прайсе RC Spark ограничен100000fetch/day/project; обновления по запуску/кеширование сохраняются. Это частичное использование Firebase, а не полный перенос в Firebase.

Энергия50/бонус30за8ч/5тапов20/приглашения/владелец покупки/серверное время/повторы/раунды/рейтинг остаются серверными. На новой БД нужно заново доказать транзакционность и пройти существующие проверки; APK144 не подходит для установки без нового endpoint и проверенной инфраструктуры. UI141 менять не требуется. Старую SQL-базу не импортируем и Telegram не переносим.

Google Play Developer API вызывается с сервера независимо от выбора хостинга: [официальная настройка](https://developers.google.com/android-publisher/getting_started). Его доступ и владение старыми покупками — отдельные незавершённые пункты.

**Существенное ограничение:** Google Play RTDN использует Google Pub/Sub, для которого [официальный quickstart](https://docs.cloud.google.com/pubsub/docs/publish-receive-messages-client-library) требует включённую оплату Google Cloud. Yandex Cloud не заменяет эту зависимость автоматически. Без GCP billing нужны проверка покупки/восстановления, серверная сверка подписок по расписанию и обработка отменённых покупок через Developer API; изменения вне игры будут приходить с задержкой выбранного интервала. Бонусы/права нельзя выдавать по клиентскому флагу или просроченному кешу. Это надо согласовать и проверить, а не объявлять RTDN готовым.

Отдельно [ограничения Google Play для покупателей в Беларуси](https://support.google.com/googleplay/android-developer/answer/11950272?hl=en) действуют независимо от сервера игры. Смена Firebase на Yandex/Supabase сама по себе их не устраняет.

## Рекомендованный следующий шаг

Сначала проверить создание и активацию платёжного аккаунта Yandex Cloud с настоящими белорусскими данными и допустимой картой; без ресурсов и переноса игры до подтверждения оплаты/доступности. Если аккаунт активируется, подтвердить выбор гибридной схемы и допустимую задержку сверки подписок, затем оценить бюджет на тестовом сценарии и переносить сервер/новую БД. Если важнее фиксированная ежемесячная цена — выбрать отдельный VPS Hostland с проверкой существующего способа оплаты.

Для полного Firebase остаётся один обоснованный, но неподтверждённый путь: письменный ответ Google Billing Support/партнёра о приёме этого плательщика с понятной комиссией и сохранением владения проектом. Публичное исследование завершено; внешнее подтверждение и активация ещё не выполнены.

## Уточнение архитектуры пользователем — 2026-10-16 20:37 Europe/Minsk

Источник: Алексей: оставить настройки в Firebase Remote Config ради будущих A/B-тестов; рассмотреть Supabase для авторизации, рекордов и остальных данных. Подтверждённое решение пользователя — сохранить Remote Config. Supabase Auth/PostgreSQL/Edge Functions — выбранное направление обсуждения; ресурсы/оплата/перенос ещё не выполнены.

Предлагаемое распределение: Firebase Core + Remote Config (и Google Analytics, когда отдельно настраиваются эксперименты); Supabase Auth для единой игровой идентичности, PostgreSQL для профиля/энергии/покупок/раундов/рейтинга/приглашений, Edge Functions/SQL RPC для доверенных операций. Firebase Auth технически не нужен одному Remote Config; две параллельные игровые авторизации не планируются.

Проверка кода: AndroidFirebaseConfig.load вызывает FirebaseMobileClient.initialize, который создаёт Firebase anonymous user; при переходе на Supabase это связывание надо убрать. Сервер firebase-android/functions/src/index.js читает только default android_config_v1 и отклоняет conditionalValues. Поэтому простое сохранение Remote Config НЕ означает готовность A/B: нужно разделить клиентские экспериментальные параметры и доверенную серверную политику, сохранять версию раунда/покупки и согласованность рейтинга. Экономические эксперименты требуют проверяемого сервером назначения варианта; присланная клиентом сумма не считается основанием начисления. Для начала предпочтительны UI-эксперименты, не меняющие награды/сложность общего рейтинга.

Официальные Firebase A/B Testing требуют Google Analytics: https://firebase.google.com/docs/ab-testing/abtest-config . В текущем AndroidManifest.xml collection deactivated=true; пользователь этим сообщением не поручал немедленно включать сбор аналитики или запускать эксперимент. При будущей настройке нужны корректные события целей и применимые настройки согласия/возраста. Источник интеграции Flutter: https://firebase.google.com/docs/analytics/get-started?platform=flutter .

Следующий шаг основного перехода: проверить регистрацию/допустимую оплату Supabase с реальными данными до реализации замены. GCPBlaze/Firestore deployment не продолжать по старому плану автоматически; архитектура пересматривается. PubSub/PlayRTDN и старые receipts остаются отдельными вопросами.
