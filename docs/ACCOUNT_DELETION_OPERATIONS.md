Контакт подтверждён Алексеем 09.10.2026: support@untouch.fun. Публичная инструкция: https://untouch.fun/delete-account/. 10.10.2026 Алексей подтвердил приём писем и переадресацию на свой skeptickdev@gmail.com; это пользовательская проверка, агент тестовых писем не отправлял. Проверка фактического хранения Hostland/production исполнения остаётся отдельно.

## Приём и подтверждение владения

1. Получить явный запрос владельца по email. Уточнить платформу: эта процедура относится к Android, не к Telegram. Не запрашивать пароль, OTP, секрет установки или банковские реквизиты.
2. Найти профиль по нику/ID. До выдачи проверочного задания зафиксировать точный `mobile_players.id` в защищённой записи обращения; не в Git или публичном журнале.
3. Для гостевого профиля с доступом выдать случайный проверочный ник (5–24 допустимых букв/цифр, без чужих данных). Владелец меняет его в игре; оператор проверяет изменение именно у ранее найденного ID на сервере. Новый профиль с таким ником, скриншот или знание публичного рейтинга доказательством не являются. Не удалять на основании одного ника/ID.
4. При утрате доступа запрос всё равно принимается без переустановки. Проверить доступные доказательства; если надёжной связи с владельцем нет, объяснить ограничение. В сборке1.0.48+49 Google включён по выбору игрока. Для связанного профиля владелец может восстановить доступ через Google, затем выполнить проверочное изменение ника в игре; один адрес email без доказательства доступа к связанному профилю не является подтверждением владения.
5. Сообщить состав данных, срок исполнения и необратимость. Не отправлять сообщения автоматически: каждое письмо требует поручения пользователя. Алексей подтвердил срок до 30 календарных дней после проверки владельца и готовность проверять обращения/передавать их на исполнение 09.10.2026. Удаление из рабочей базы завершить в этот срок; резервные копии и журналы учитывать отдельно.

## Исполнение оператором

Не запускать удаление для реального игрока без подтверждённого запроса и проверки владения. Использовать транзакцию, остановить операции удаляемого профиля на время удаления и проверить все связанные таблицы. Перед COMMIT проверить точный ID; откатить транзакцию при несоответствии. Не создавать бессрочный экспорт удаляемых персональных данных «для подстраховки».

Состав по коду `telegram-web/api/mobile_store.php`:

| Таблица | Условие |
|---|---|
| mobile_players | id = проверенный числовой ID; здесь также google_sub и wallet_json |
| mobile_devices | player_id = ID; все устройства |
| mobile_rounds | player_id = ID; включая незавершённые попытки |
| mobile_operations | player_id = ID |
| mobile_purchases | player_id = ID; сейчас реальные покупки отключены |
| mobile_names | owner = `android:ID` |
| scores | user_id = `android:ID`; нельзя удалять по одному player_name |

Удалять связанные строки, затем профиль. После операции проверить нулевые количества во всех семи таблицах, недействительность прежней авторизации и отсутствие результатов в рейтинге. Не затрагивать Telegram-профиль и одноимённые старые результаты без надёжной привязки.

При будущем включении покупок сначала внедрить политику минимального антифрод-хранения и возвратов: простое удаление журнала токенов может позволить повторную выдачу покупки. Не хранить платёжные данные без цели и срока; сообщать исключение владельцу. Подписка отменяется пользователем в Google Play отдельно.

## Остаточные данные

- Проверить текущие настройки Hostland для БД, резервных копий и access/error logs. Публичная документация описывает 14 дней стандартных копий, не доказывает настройки аккаунта.
- При восстановлении старой базы повторно применить ранее исполненные удаления до возврата сервиса в работу. Минимальный реестр исполнения хранить защищённо; срок и доступ назначить отдельно.
- Сопоставить и убрать ненужные письма/вложения после завершения обращения; не копировать их в память проекта.
- Сообщить заявителю фактический результат, остаточные категории, их основание и срок. Нельзя обещать мгновенное удаление из всех копий.

## Приватный инструмент: последовательность оператора

Выполнять только после конкретного разрешённого обращения и проверки владения. Агент не выполнял настоящий запрос удаления. Разместить инструменты вне публичного каталога на сервере с существующей защищённой настройкой БД; путь `require` должен соответствовать фактическому расположению серверных исходников. Не переносить пароль в аргументы команды. Удостовериться, что все семь таблиц InnoDB; исполнение проверяет это само, миграций не делает.

1. Закрепить ID профиля **до** выдачи случайного проверочного ника. Дождаться его изменения именно у этого ID и записать факт проверки владения в защищённом обращении.
2. Предварительный просмотр: `php tools/delete_mobile_account.php --id=android:123`. Это только чтение; возвращаются количества семи таблиц и fingerprint записи, без секрета/Google subject/кошелька.
3. Перед реальным исполнением остановить Android-записи на сервере и дождаться завершения уже открытых запросов. Это обязательное условие для опубликованного API1.0.6; одного блокирования строки недостаточно для устаревших обработчиков. Не использовать выключение всей Telegram-базы; согласовать короткое обслуживание Android. Доступ и запуск обслуживания пока не подтверждены.
4. Запустить вручную с точным ID, проверочным ником и fingerprint предварительного просмотра: `php tools/delete_mobile_account.php --id=android:123 --execute --challenge=VERIFIED_RANDOM_CHALLENGE --fingerprint=REVIEW_FINGERPRINT --confirm="DELETE android:123" --maintenance-confirmed`. Здесь показаны примеры, не реальные значения. Изменившаяся запись/другой ник/повтор отклоняются; ошибка откатывает транзакцию.
5. При наличии purchase-записей production исполнение останавливается: сначала нужна отдельно проверенная политика минимального хранения/возвратов. Override разрешён только инструментальному тесту с одноразовым `_untouch_mobile_test_*` prefix, не production CLI.
6. Проверить нули в семи таблицах, недействительность всех прежних секретов и исчезновение результатов из общего рейтинга. Разблокировать записи только после проверки. Локальный кэш/приложение пользователя автоматически не очищаются серверной процедурой; объяснить удаление локального кэша отдельно без передачи секрета.
7. Зафиксировать минимальный защищённый факт исполнения для повторного удаления после восстановления резервов. Проверить фактические сроки копий/журналов Hostland, завершить переписку по поручению владельца.

В новом Android-кандидате ссылки и копирование ID реализованы; реальные сроки Hostland, доставка email и производственная установка приватного CLI ещё не подтверждены. Успех изолированного теста не означает уже работающий опубликованный endpoint или полный цикл настоящего обращения.
